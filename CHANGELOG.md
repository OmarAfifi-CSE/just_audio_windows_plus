## 0.5.6

* **A Seek Back To An Already-Open Item Now Lands Physically**: `MediaPlaybackList`'s keep-open window never re-fires `MediaOpened` for an item that is still open, so a cross-item `seek` targeting it deferred forever: the requested position was only *reported* (the fake-position window) for two seconds and then silently reverted to the stale one — a paused scrubber visibly jumped back. The deferred seek is now applied when the item switch settles (`CurrentItemChanged` applies it whenever the pipeline is not mid-open; `Opened()` remains the path for fresh items), guarded against the transitional no-current-item window. Pinned by real Windows playback scenarios in both the paused and playing variants, sampled past the fake-position deadline.
* **Rapid Cross-Item Scrubbing No Longer Stalls Playback**: Back-to-back seeks across items (a user dragging a scrub bar) could leave the session paused behind a truthful-looking position: the `Play()` issued alongside the seek was swallowed while the pipeline was still switching. `SeekCompleted` now re-asserts `Play()` once the pipeline confirms the seek landed, and `Broadcast()` self-heals a paused session whenever Dart's playing intent is unambiguous (excluding loading, seeking, completion and the end-of-media window, where a re-play would restart a finished track). Pinned by a four-seek scrub scenario that requires the position to continue advancing from the final target, and by an eight-cycle pause/seek/play toggle storm proving the re-assertion is strictly one-directional: a user-issued pause always stops the clock and a user-issued play always restarts it.
* **Removing The Playing Item Advances Playback**: A `concatenatingRemoveRange` that removed the current item left the list with no current item: every broadcast carried a null duration and index, and playback wedged. The mutation now advances to the item that shifted into the removed item's position (starting it from its beginning), exactly as the Android implementation does; a surviving current item keeps its position, and emptying the playlist still completes. Pinned by a real playback scenario and three Dart contract tests.
* **A Reorder That Shifts The Current Item No Longer Wedges Later Seeks**: A `concatenatingMove` that shifted the playing item to a new index armed a deferred seek and relied on an event to consume it — but `MoveTo` back onto the *same* item object fires no `CurrentItemChanged`, and an already-open item fires no `MediaOpened`, so the arm was never consumed and every later same-item `seek` deferred onto it forever (the requested position only ever appeared as the 2-second fake position). The mutation now applies the preserved position directly when the surviving item is the one the session already describes; if WinRT chose to re-open the item for the move, the arm stays and `Opened()` lands it. Pinned by a real playback scenario and a Dart contract test.
* **The Requested Initial Position Is Reported While Loading**: `load(initialPosition:)` armed the deferred seek for the open, but the loading-time broadcasts reported the fresh session's `0` — a seek bar jumped from zero the moment the item opened. The fake-position window is now armed at load time, so loading events carry the requested position; the existing 2 s deadline still guards a pathologically slow open. Pinned by a playback scenario against a deliberately delayed HTTP server.
* **A Play After A Failed Load Can No Longer Resurrect The Old Source**: A replacement `load` whose items fail to construct (e.g. a relative URI WinRT rejects) throws while the *previous* source is still attached; `Fail()` paused it but never detached it, so a `play()` pressed on the failed engine resumed the orphaned track under an app that believed the player was idle — and the play settled instantly while the ghost audio ran. `Fail()` now detaches the source outright (every `Play()` site becomes a no-op until the next successful load re-arms the engine) and the play handler additionally refuses to `Play()` a failed engine. Pinned by a real playback scenario sampling the position across probes after the play.
* **The Deferred-Seek Arm Is Now Event-Driven, Not One-Shot**: the arm had exactly one consumer per path — `CurrentItemChanged` for kept-open items, `Opened()` for fresh ones. If that single sample caught the pipeline mid-open (or its `Position()` call threw transiently), nothing ever consumed the arm: the requested position lived only as the two-second fake window and every later same-item seek deferred onto a dead arm forever. `Broadcast()` now retries an armed-but-unapplied seek on every broadcast, so the first event after the transient window passes lands the position; `Opened()` also declines to apply when the item that opened is not the arm's target (a cross-item seek racing the load's in-flight open), leaving the retry to converge instead of landing on the wrong item.
* **`await play()` On A Completed Player Now Resolves At The Replayed End**: the handler called `Play()` — which restarts the ended list — and then settled the incoming play future instantly because `completed_` was still set, so `await player.play()` returned the moment the replay *started*. The completed state is not terminal once the handler has re-armed it; only a failed engine or a loaded-but-empty playlist settle instantly now, matching the Android implementation. The end-of-media self-heal was hardened in the same pass: a 250 ms position margin (container/VBR duration skew, not a few milliseconds) plus a one-pump-turn deferral that lets the simultaneously-queued `MediaEnded` task cancel the heal before any re-play — two independent barriers against double-playing a finished track.
* **Exception-Safety Sweep (stop, Mutate, Enqueue)**: `stop` clears the seek bookkeeping *before* its COM rewind so a transient `Position()` throw cannot leave an armed deferred seek to undo the rewind; `pause`/`stop` guard their COM calls individually; `Mutate`'s post-commit `MoveTo` calls (surviving-item re-selection and removal advance) are best-effort — a transient throw no longer errors the mutation *after* the tree and list edits are committed, which diverged Dart's tree from the native list; and `Enqueue`'s `Post` is contained so an allocation failure inside a WinRT callback cannot escape through the WinRT raise boundary. A `seek` on an idle or failed engine is now a true no-op that reports no fabricated position.
* **A Seek Issued While The Load Is Still Pending Is No Longer Lost**: A same-item or unindexed `seek` that arrived while the media was still opening set the session position directly, but the pipeline discards that position when the item opens, and `Opened()` then applied the *load's* deferred initial position — silently clobbering the user's scrub. Such a seek now overwrites the deferred target and keeps it armed, so the newest position is the one that lands when the media opens. Pinned by a Dart contract test, a native time-conversion test, and a real Windows playback scenario against a deliberately delayed HTTP server.
* **A Failure Now Silences Native Audio**: `Fail()` reports `idle` to Dart, but on the replacement-load failure path (e.g. a new playlist whose second item fails to construct) the *old* source was still attached and kept sounding while Dart believed the player was idle. `Fail()` now pauses the native player before broadcasting, so the engine's audio state and Dart's belief always converge. `Fail()` also drops the deferred seek now: no `Opened()` is ever coming to consume it after a failure, so a later same-item `seek` would have taken the deferral branch and deferred onto a dead arm forever (the reported position would never land in the session). This mirrors `stop`'s hygiene and the pinned contract in the Dart mock.
* **Extreme Positions Can No Longer Overflow The TimeSpan Conversion**: `TimeSpan` counts 100 ns ticks, so a caller-supplied microsecond value near `int64_t` max overflowed the tick conversion (undefined behaviour). Every user-input → `TimeSpan` boundary (seeks, initial positions, clipping bounds) now goes through `MicrosToTimeSpan`, which clamps to the representable range; ordinary values round-trip unchanged.
* **The iOS-Only AVPlayer Setters Are Accepted Again**: `setAutomaticallyWaitsToMinimizeStalling`, `setCanUseNetworkResourcesForLiveStreamingWhilePaused` and `setPreferredPeakBitRate` sit on `AudioPlayer`'s cross-platform API, and `just_audio` forwards them over the method channel whenever the app calls the setter (or platform activation finds a non-default value). Answering `NotImplemented` surfaced a `MissingPluginException` from a plain public API — a compatibility regression against `just_audio_windows` 0.2.3, which accepted them as no-ops. They now round-trip as accepted no-ops again, pinned by a Dart contract test.
* **Dead Code Removed**: Dropped the unused `TimeSpanToMilliseconds` helper, the never-invoked `JustAudioEventSink::Error` (playback failures travel in-band through the state map's `errorCode`/`errorMessage`, exactly as on Android), `PlatformThreadDispatcher::on_platform_thread` and its now-purposeless `platform_thread_id_` member (a leftover from the old synchronous seek paths), and the standalone `ReorderByShuffleOrder` helper (the production shuffle path has been `SourceNode::Permutation` + `Order` since 0.4.0). The README's architecture section no longer advertises the standalone helper.
* **`JustAudioWindowsPlus.isSupported` Is A Plain Public Constant**: The `@visibleForTesting` annotation on the package's only public symbol warned downstream consumers who read it with the standard lint set. It is now a normal documented constant.
* **Documentation Truthfulness**: The README's architecture section still described `generation_` as non-atomic; it became atomic in 0.5.5 for the cross-thread recovery entry point. Test counts across the README, CI workflow and test guide now match the suites (107 Dart contract tests, 40 native C++ tests, 42 real playback scenarios).

## 0.5.5

* **Platform-Thread Dispatch Drains Unconditionally**: `Drain()` previously stopped draining its already-swapped queue when the window was destroyed mid-dispatch (`if (!available()) break`), partially abandoning a batch that had already been dequeued. The swapped vector is now drained unconditionally — running after `window_` is gone is safe, since task ownership is via `weak_ptr`/`generation_` — so a dispatched batch is never half-processed. This is defensive hardening: in the normal teardown path `Dispose()` settles `pending_load`/`pending_play` before `Shutdown()`.
* **Playlist Mutation Rollback Is Now In-Place, Not Destructive**: `Mutate()`'s snapshot is now `try` guarded (COM `GetAt`/`Size` can throw before mutation starts) and the rollback is in-place (`RemoveAtEnd`/`Append`/patch by index) rather than `Clear()+Append`. The old `Clear` before `Append` could OOM on `Append` and truncate the `MediaPlaybackList` to zero precisely when recovery was most needed (correlated OOM). Double-OOM during rollback now falls back to an empty list (logged, requires next `load()` to reconverge) rather than a half-truncated divergence.
* **Recovery Broadcast Is Generation-Aware, Lossless, and Bounded**: `PostRecoveryBroadcast()` now captures `generation_at_post`, checks `disposed_ || generation_ != generation_at_post` at drain time, checks the `Post()` return value, and uses a `ReschedulingGuard` plus `recovery_reschedule_requested_` to coalesce without losing nested failures. A stale recovery cannot corrupt a fresh `Load`, and a `PostMessageW` quota-full failure (or a `Post()` allocation throw) no longer leaves `pending=1` forever. Retries are now bounded: delivery failures that persist across several recovery rounds abandon the loop instead of spinning forever, and the budget resets on any successfully delivered state event. The rescheduler is also contained against throwing — it runs in a noexcept destructor. `generation_` is now atomic because the capture happens before the post, off the dispatcher thread.
* **`play()` Coalescing Settles the Second Request, Not the First**: Rapid successive `play()` calls are coalesced at one pending `MethodResult`. The request that arrives while one is already in flight is now settled immediately with "play accepted" semantics — matching just_audio's contract ("if the player is already playing, this method completes immediately" and its directive that the platform "ignore the second play request since it is already playing"). The request already bound to the playback lifecycle stays pending until pause/stop/end/fail, so a concurrent second request can no longer resolve the first caller's `await player.play()` early. `pending_play_` remains bounded at one.
* **Rapid Scrub Ghost-Snap Window Narrowed**: `SeekCompleted` completions are now qualified by an atomic `seek_generation_` captured on the WinRT thread-pool before `Enqueue`. A completion whose callback ran before a newer `BeginSeek` is ignored at drain time, so an earlier seek's already-queued completion can no longer clear a newer seek's fake-position window (`target_seek_position_`) and snap the scrubber backward. (A completion the OS delivers only after a newer seek has begun remains indistinguishable from that seek's own completion — WinRT emits no correlate — which the 2 s deadline bounds.) `BeginSeek`'s 2 s deadline is now simply pushed forward by every new seek.

## 0.5.4

* **`await player.play()` No Longer Resolves Before Playback Starts**: 0.5.4's first draft settled any `play` that arrived with no source attached. That is wrong: `just_audio` activates the platform by sending `play` *before* `load`, so the normal first-play path hit that branch and `await player.play()` returned before the track started. A play is now settled only when the state is *stably* unplayable - the media already ended, the engine failed, or a loaded playlist is empty. A source-less play stays pending, which is the `just_audio` contract, and the load that follows settles it.
* **Shuffle Order No Longer Applied While Shuffling Is Off**: `just_audio` sends a permuted `shuffleOrder` with *every* load, shuffle mode notwithstanding, and `SetShuffledItems` defines the playback list's automatic progression regardless of `ShuffleEnabled`. The engine applied that permutation unconditionally, so any playlist of three or more tracks played out of order with shuffling disabled. `ApplyShuffle()` is now gated on `shuffle_mode_ == 1`.
* **Redundant Player-Data Events Removed & Self-Healing Delivery Hardened**: The data channel carries *intent* (`playing`, volume, speed, loop and shuffle), and `just_audio` applies every value it receives. Republishing an unchanged value previously let a stale copy overwrite a decision Dart had already made (causing silent playback in Release). `PublishData()` now deduplicates intent updates and commits `published_data_` exclusively upon successful sink delivery (`commit-on-success`), while recovery broadcasts bypass deduplication (`force_data`) to guarantee permanent state convergence without desync.
* **Transactional Playlist Mutation Rollback**: `Mutate()` now snapshots the original `MediaPlaybackList` items prior to applying in-place insertions or deletions. If a WinRT COM exception or resource exhaustion occurs mid-mutation, the live playback list is transactionally restored to its pristine pre-mutation state before propagating the error to Dart, eliminating desynchronization between native items and the C++ source tree.
* **Dispatcher Task Diagnostics & Exception Containment**: `Drain()` runs inside a `WndProc` boundary and logs any caught task exceptions with actionable diagnostic identifiers. Recovery broadcasts explicitly capture and route native exceptions through `owner->Fail(...)` instead of silently dropping state events.
* **An Invalid `load` No Longer Tears Down A Working Player**: An out-of-range `initialIndex` or negative `initialPosition` was validated inside `Load()`, which runs *after* the request result has moved into `pending_load_`. A throw there could only be reported through `Fail()`, so a plain argument mistake published a playback error, rolled the source back, and left the already-loaded media unusable. The initial seek is now validated while the call still owns its result, so it is reported as `argument_error` and the loaded source is untouched.
* **A Throwing Task Can No Longer Reach The Message Loop**: `Drain()` runs inside a `WndProc`, which is a C callback boundary, and an exception escaping it would terminate the process. Tasks are now contained there. Every task the plugin posts already handled its own errors; this is the backstop that keeps a bug in one of them from being fatal.
* **`stop` Drops The Deferred Seek Too**: Stopping rewound the session and cleared the in-flight seek, but left the deferred seek armed. `Opened()` applies that deferred position when the item opens, so the rewind was undone moments later. A stop before an item finished opening therefore snapped back to the old position.
* **`bufferedPosition` Is Clamped To The Duration**: `bufferedPosition` drove app buffer bars and could exceed the duration, because a position sample taken mid-item-switch is not bounded by the reported duration. It is now clamped. The position itself is deliberately *not* clamped: across an item switch the session can still be describing the previous item, and clamping to that stale duration would report a position the user never seeked to.
* **Playlist Mutations Read The Position Safely**: `Mutate()` reads the playback position to preserve the timeline across a reorder. That read is now guarded like the equivalent read in `Broadcast()`, because WinRT can throw while the pipeline is switching items; previously a transient failure there failed the whole mutation.
* **Source Rolled Back On Failure**: `Fail()` now clears `source_set_`, so a failed source can no longer leave the engine believing media is attached. This is the rollback the 0.4.0 notes below describe; it had been dropped when the atomic fields were removed, and is now enforced explicitly. A subsequent `load()` re-arms it, so retrying after a failure still works.
* **Dead Code Removed**: Dropped the unused `JAW_TRACE` macro, `ValueOrNull`, and `TryGetInt64` from `player.hpp`, and added the previously omitted `uri_utils.hpp` to the CMake source list. The `generation_` token is intentionally not atomic, because the platform-thread dispatcher already serializes every access; see the 0.1.0 and 0.4.0 corrections below.
* **Contract Tests Now Test the Real Contract**: The Dart suite previously asserted behaviour the native engine does not implement - it accepted negative seek positions, out-of-range playlist indices, `setPitch`/`setSkipSilence` with no arguments, empty removal ranges, and a `concatenatingMove` target equal to the list length, and it invented error codes (`load_error`, `concatenatingMove_error`, ...) that the engine never emits. The fake engine is now a faithful model of `player.hpp` and `source_model.hpp`, including the mandatory per-source `id`, the mandatory `shuffleOrder` permutation on every concatenating source and mutation, the real `argument_error`/`unsupported`/`abort`/`disposed` codes, and the deferred `play()` semantics. It also models the data-channel dedupe and the play-settle rule, so a divergence between fake and engine fails the Dart suite.
* **Documentation Corrections**: Corrected claims that the code did not support - the generation token is not atomic, the production shuffle path is `SourceNode::Permutation` + `Order` rather than `ReorderByShuffleOrder` (which is a standalone helper used only by its own tests), callbacks are dropped rather than delivered when a dispatcher is gone rather than "100% of callbacks executing cleanly", and FLAC/HLS/DASH support is OS-dependent rather than guaranteed. See the corrections to the 0.1.0 and 0.4.0 entries below.
* **Superseded 0.1.0 / 0.4.0 Notes**: Those entries describe `std::atomic<bool> disposed_`, `std::atomic` `source_set_`/`loop_mode_`/`shuffle_mode_`, and a `std::recursive_mutex player_mutex_`. None of those exist in the current engine. They were removed in favour of the `PlatformThreadDispatcher` design described in the 0.2.0 notes, which serializes all player state onto the platform thread and makes the atomics and the recursive mutex unnecessary. They are left in place as a historical record of what shipped in those releases.
* **CI Now Runs the Playback Suite**: The workflow executes the real Windows playback scenarios and the example's widget test, so the verification claims in the README are enforced on every push rather than only documented.
